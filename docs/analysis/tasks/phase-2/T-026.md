# T-026: Cascade guard in `UninstallModuleCommand`

- **ID:** T-026

- **Phase:** phase-2
- **Milestone:** A
- **Created:** 2026-04-24

## Context

Uninstalling a module that another installed module depends on leaves the
dependent broken (missing tables, missing integration-event consumers,
missing permission keys). [ADR-0028](../../../decisions/0028-module-uninstall-data-retention-contract.md)
formalizes the contract: the uninstall command MUST refuse when an installed
dependent remains, with an opt-in `--cascade` that uninstalls the full subtree
transactionally in reverse-dependency order.

- Phase file: [`../../../roadmap/phases/phase-2-enterprise.md`](../../../roadmap/phases/phase-2-enterprise.md) (milestone A)
- Related ADRs: [ADR-0028](../../../decisions/0028-module-uninstall-data-retention-contract.md) §Implementation notes (uninstall contract); [ADR-0031](../../../decisions/0031-cascade-uninstall-per-module-transactions.md) (cascade transaction policy — supersedes ADR-0028's outer-transaction model)
- Sibling tasks: T-025 (cleanup job), T-027 (GDPR escape hatch)

## Acceptance criteria

- [ ] `UninstallModuleCommand` gains a boolean `Cascade` parameter (default
      `false`).
- [ ] Before uninstalling, handler consults the DI-registered
      `IEnumerable<IModule>`, walks the dependency graph, and collects every
      installed module that declares the target in its `Dependencies`. If the
      set is non-empty and `Cascade = false`, the handler returns
      `Result.Failure<Unit>(LocalizedMessage.Of("lockey_identity_error_module_uninstall_blocked_by_dependent", new { Dependents = ...}))` —
      no partial work done.
- [ ] `Cascade = true` path: uninstalls modules in **reverse-dependency
      order** (deepest first) so the root module's drop is last.
      **Transaction boundary: per-module, NOT a single shared transaction
      across all modules** — this is the normative cascade model per
      [ADR-0031](../../../decisions/0031-cascade-uninstall-per-module-transactions.md)
      (which supersedes ADR-0028's outer-transaction-with-savepoints
      paragraph because the original mechanism is not implementable
      under per-module DbContext isolation + ADR-0001's no-DTC rule;
      see ADR-0031 §Context for the full chain).
- [ ] **Mutual exclusion across the cascade**: a session-scoped
      `pg_advisory_lock(hashtext('uninstall:' || tenantId))` (NOT
      `pg_advisory_xact_lock`) is acquired before the first module
      step and released in `finally`. The lock spans multiple module
      transactions; a transaction-scoped lock would release between
      modules and let a concurrent operator interleave a second
      cascade.
- [ ] **Forward log + observable partial failure**: the orchestrator
      maintains an in-memory `successes` list of modules whose
      per-module transaction committed. On failure at module N:
      rollback that module's transaction, emit a
      `ModuleUninstallFailedIntegrationEvent` carrying
      `successes_so_far` + `failed_module` + `error_lockey`, throw
      `CascadePartialFailure` (in `Nexora.SharedKernel.Abstractions.Modules`)
      so the caller surfaces the partial state. **Earlier modules'
      uninstalls are NOT auto-undone** — the rename-to-`_del_` per
      ADR-0028 is the compensation primitive (operator reinstalls
      within retention if they want to back out). Modules MAY override
      `OnUninstallAsync` to publish module-specific compensating
      actions; the default no-op is acceptable for the rename-back
      path. Integration test `Tests: Integration` row below MUST
      exercise: two-module chain where deepest succeeds and root
      fails — assert the forward log shows the deepest as a success,
      the failed event payload carries it, and the deepest module's
      `_del_` tables are intact (recoverable via reinstall).
- [ ] Locale key `lockey_identity_error_module_uninstall_blocked_by_dependent`
      added to en + tr bundles; message carries the dependent-module list.
- [ ] Audit: every uninstall (whether single-module or cascade step) emits the
      existing `ModuleUninstalledIntegrationEvent` via outbox (ADR-0028
      extended schema: `CanonicalTableNames` + `RenamedTableNames` + `UninstalledAtUtc`).
- [ ] Tests:
  - Unit — `UninstallModuleCommandHandlerTests`: no dependents → succeeds;
    dependents + no cascade → failure with lockey; dependents + cascade →
    transactional reverse-order drops.
  - Integration — two installed modules where B depends on A: attempting to
    uninstall A without cascade fails; with cascade succeeds and B's tables
    drop first.
- [ ] Permission: the existing `identity.modules.uninstall` permission is
      sufficient (no new permission needed — cascade is a parameter, not a
      separate operation).
- [ ] Docs: `docs/modules/tier-1-core/identity/SPEC.md` §Uninstall gains the
      cascade flow and dependent-blocking rule.

## Technical notes

- Dependency walk uses the same topological helper as `DemoDataSeeder.OrderByDependencies`;
  factor it into `Nexora.SharedKernel.Abstractions.Modules.ModuleDependencyGraph`
  so both callers share one implementation.
- Cascade transaction MUST carry the platform-admin identity through every
  step — use `ITenantContextAccessor` snapshot/restore if the inner step
  switches tenant context.
