## Context

Per ADR-0003, production migrations must be additive. An architecture test is needed
to enforce this mechanically — scan every `Migration.Up` method and fail CI on
`DropColumn`, `RenameColumn`, or narrowing `AlterColumn`. Without this guard,
regressions are only caught in review.

See `docs/operations/migration-orchestration.md` §1.2.

## Acceptance criteria

- [x] `tests/Nexora.Architecture.Tests/AdditiveOnlyMigrationTests.cs` —
      4 `[InlineData]` `[Theory]` rows (DropColumn, DropTable, RenameColumn,
      RenameTable) + 1 `[Fact]` for AlterColumn (which fires unconditionally,
      relying on the allowlist marker for any legitimate use) + 1 `[Fact]`
      self-test that constructs a synthetic destructive migration and a
      synthetic allowlisted one in a temp dir to prove the scanner fires
      AND honours the marker.
- [x] Scans recursively under `src/**/Migrations/*.cs` (EF Core's generated
      location convention) — module additions are picked up automatically
      with no per-module configuration.
- [x] Failure message points at the file + line + offending operation +
      remediation (rename to add-new + dual-write, add allowlist marker,
      etc.). `*.Designer.cs` skipped (snapshot diffs, not actual SQL).
      Source text is stripped of comments + string literals before
      matching so a doc comment that mentions
      `migrationBuilder.DropColumn(...)` in prose cannot false-hit.
- [x] Allowlist marker:
      `// architecture-allow: destructive-migration ADR-NNNN`. The
      four-digit ADR reference is part of the regex so the destructive
      change is paired with documented decision-record reasoning;
      without an ADR, the marker fails the test (the regex won't match).
