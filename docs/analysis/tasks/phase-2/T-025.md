## Context

Module uninstall uses a 30-day rename-and-retain pattern ([ADR-0028](../../../decisions/0028-module-uninstall-data-retention-contract.md)) —
tables are renamed to `{module}_{table}_del_{timestamp}` rather than dropped, so
reinstall within the retention window can restore data and auditors still see
the evidence. The contract is only complete once a cleanup job actually
**drops** the renamed tables after the retention window expires. Without this
job, uninstalled-module tables accumulate indefinitely and violate the 30-day
retention promise made in the admin UI.

## Acceptance criteria

- [ ] `PurgeUninstalledModulesJob` extends `NexoraJob<PurgeUninstalledModulesParams>`
      and is decorated `[Queue("maintenance")]` +
      `[DisplayName("platform:purge-uninstalled-modules")]`.
- [ ] Registered as a recurring Hangfire job at **03:00 UTC + per-tenant
      deterministic jitter**. The jitter formula MUST be **stable across
      process restarts and hosts** — `Guid.GetHashCode()` is explicitly
      non-stable in .NET (each process randomises the hash seed) and
      MUST NOT be used. Use a cryptographic or content-addressed hash
      with an **overflow-safe non-negative conversion**:
      `var hash = BitConverter.ToInt32(MD5.HashData(tenantId.ToByteArray()), 0);`
      `var offsetMinutes = (hash & 0x7FFFFFFF) % 120;`
      The `& 0x7FFFFFFF` mask clears the sign bit, producing a value in
      `[0, int.MaxValue]` regardless of the input. **Do NOT use
      `Math.Abs(hash)`** — it throws `OverflowException` for
      `int.MinValue` (which has no positive counterpart in two's
      complement), and MD5's output distribution gives that value a
      ~1-in-4-billion chance per tenant — small but non-zero and
      operationally awful when it hits. MD5 is fine here — not a
      security-critical usage, the requirement is stability + uniform
      distribution. The
      resulting `offsetMinutes` spans 0–119; derive **both the hour and
      the minute** so a 75-minute offset maps to `15 4 * * *` (04:15 UTC),
      not `75 3 * * *`. Concretely: `hourOffset = offsetMinutes / 60`
      (0 or 1); `minuteOffset = offsetMinutes % 60` (0–59); final cron is
      `{minuteOffset} {3 + hourOffset} * * *`. Rolling-window scheduler
      is an acceptable alternative provided no two tenants in the same
      cluster start within the same 30-second slice. Why mandatory:
      a stock `0 3 * * *` cron fires every tenant's `DROP TABLE`
      simultaneously and thundering-herds Postgres WAL writers.
- [ ] Per tenant: scan `PlatformDbContext.TenantModules` where
      `IsDeleted = true AND (DeletedAt + retention_days) < now()`; retention
      resolved via `IConfigurationResolver.GetAsync<int>("modules.uninstall.retention_days")`
      (default 30, cap-bounded per ADR-0028).
- [ ] For each due row: process `TenantModule.DeletedTableNames` (which is
      stored as a CSV `string?` — see
      `src/Modules/Nexora.Modules.Identity/Domain/Entities/TenantModule.cs`,
      NOT a collection) with **two layers of safety** and partial-success
      retry semantics:
      1. **Parse the CSV** into a `List<string>` of table names via a new
         domain helper on `TenantModule` (`IReadOnlyList<string> ParseDeletedTableNames()`
         or equivalent); do NOT split the CSV inline in the job.
      2. **Whitelist validation before interpolation.** The canonical
         shape is `{module}_{entity}_del_{timestamp}` (snake_case
         module + entity). T-026's uninstall path may emit either
         contiguous `yyyyMMddHHmmss` (14 digits) or
         `yyyyMMdd_HHmmss` (8+`_`+6 digits) — accept BOTH so a
         T-026 implementer choosing either format does not break this
         purge step. Validate each parsed entry against the regex
         `^[a-z][a-z0-9_]*_del_(?:[0-9]{14}|[0-9]{8}_[0-9]{6})$`
         BEFORE interpolating it into SQL; entries that don't match
         are logged at `Warning` with the offending string and
         **kept** in the failed list (NOT
         silently dropped — operators need to see the malformed entry
         in the next purge cycle until they fix the data manually).
      3. **Quote BOTH the schema AND the table identifier.** Schema
         names are `tenant_{guid}`; because GUIDs can start with a digit,
         PostgreSQL requires the schema to be double-quoted too. The SQL
         MUST be `DROP TABLE IF EXISTS "{schema}"."{table}" CASCADE`
         (both sides quoted). Use `Npgsql`'s identifier-quoting helper
         (`"\"" + raw.Replace("\"", "\"\"") + "\""`) or equivalent —
         never bare `{schema}."{table}"`.
      4. **Per-table try/catch** so one table failure does not block
         sibling drops. Track successes + failures in two separate
         `List<string>`s.
      5. **Reserialize the survivors.** Only the entries that failed
         (parse-rejected + DROP-rejected) get written back to
         `TenantModule.DeletedTableNames` as a CSV via a matching
         domain helper (`RemoveDeletedTableNames(successful)` or a
         direct `SetDeletedTableNames(csv)`). Set the column to `null`
         when every entry succeeded.
      6. **Hard-delete the TenantModule row IF AND ONLY IF** the
         surviving list is empty (i.e. all tables dropped successfully).
         Because `TenantModule` is an `AuditableEntity<T>` with soft
         delete, a plain `Remove(tenantModule)` would only flip
         `IsDeleted` — we need the actual row gone so a module reinstall
         does not trip the "row already exists" guard. Use the sanctioned
         hard-delete path: either `BaseDbContext.EnterHardDeleteScope()`
         (existing pattern, see T-004 WP4) before Remove + SaveChanges,
         or issue a raw `DELETE FROM identity_tenant_modules WHERE "Id" = @p0`
         through `ExecuteSqlInterpolatedAsync` on the PlatformDbContext.
         Partial-success state keeps the row in place so the next purge
         run retries just the failed tables.
- [ ] **Audit entry per purge** (ADR-0028 §Implementation notes). Map the
      spec's conceptual fields onto the actual `AuditEntry.Create(...)`
      shape from `src/Modules/Nexora.Modules.Audit/Domain/Entities/AuditEntry.cs`:
      - `Module = "Identity"` (the module that owns `TenantModule`;
        the purge job logically lives on the platform side but the
        row it erases belongs to Identity).
      - `Operation = "module.uninstall.purge"`.
      - `OperationType = "Delete"` (matches AuditEntry's existing
        enum convention for physical-delete operations).
      - `UserId = null` (no user principal on a scheduled job).
      - `UserEmail = "system:platform-purge"` (the `ActorId` surface
        from ADR-0028; `UserEmail` is the string field AuditEntry
        exposes for non-user actors).
      - `EntityType = "TenantModule"`.
      - `EntityId = {tenantModuleId}`.
      - `IsSuccess` — **success criterion is "the failed list is empty
        AND the TenantModule row was hard-deleted"**, NOT "at least one
        table was dropped". The latter would mis-report a no-op success
        as Failed: a tenant whose `DeletedTableNames` parsed to an
        empty list (e.g. the prior purge already ran and the row only
        survived because the hard-delete failed) successfully completes
        with zero drops + a row hard-delete and MUST report
        `IsSuccess = true`. Concrete rules:
        - `failedList.Count == 0 && rowHardDeleted` → `IsSuccess = true`.
        - `failedList.Count > 0` (parse-rejected + DROP-rejected entries
          remain) → `IsSuccess = false`; the row stays in place for
          retry.
        - Hard-delete attempted but failed (rare; shouldn't happen if
          `failedList.Count == 0` since the dropping path uses the same
          DbContext) → `IsSuccess = false` and the failure surfaces in
          `Metadata.hardDeleteError`.
      - `Metadata` — JSON-serialized structured payload:
        `{ "tenantId": "…", "module": "…", "retentionDays": N,
           "dropped": ["…"], "failed": ["…"], "durationMs": N,
           "hardDeleteError": "…" | null }`.
      The observability counter + metrics below are for dashboards;
      this audit entry is the **compliance record** — operators must
      answer "when was this data physically deleted, by what, and why"
      from the audit log alone.
- [ ] Observability: counter `nexora_module_uninstall_purged_total{module}` +
      histogram `nexora_module_uninstall_purge_duration_seconds`. Per-tenant
      log line with tenant id + modules purged + rows dropped.
- [ ] Integration test (Testcontainers Postgres): seed `TenantModule` past
      retention, run job, assert tables dropped + row deleted; seed another
      within retention, assert untouched.
- [ ] Tests: unit (scheduler jitter math, retention predicate) + integration
      (end-to-end drop).
- [ ] Docs: `operations/migration-orchestration.md` gains a §"Uninstall purge"
      subsection describing the schedule + retention tuning.

## Technical notes

- Drop order within a tenant: `TenantModule.DeletedTableNames` is already in
  reverse-dependency order per the uninstall path; respect it so FK cascades
  land naturally.
- The job's own DbContext MUST use the platform schema (tenant-agnostic); the
  per-tenant drop fans out via an inner scope.
- `SetTenant(...)` called per inner iteration so structured logs carry the
  tenant id even though the job outer scope is platform-wide.
