## Context

Module uninstall uses a 30-day rename-and-retain pattern ([ADR-0028](../../decisions/0028-module-uninstall-data-retention-contract.md)) —
tables are renamed to `{module}_{table}_del_{timestamp}` rather than dropped, so
reinstall within the retention window can restore data and auditors still see
the evidence. The contract is only complete once a cleanup job actually
**drops** the renamed tables after the retention window expires. Without this
job, uninstalled-module tables accumulate indefinitely and violate the 30-day
retention promise made in the admin UI.

## Acceptance criteria

- [ ] `PurgeUninstalledModulesJob` extends `NexoraJob<PurgeUninstalledModulesParams>`
      and is decorated `[Queue("maintenance")]` +
      `[DisplayName("platform:purge-uninstalled-modules")]`.
- [ ] Registered as a recurring Hangfire job at **03:00 UTC + per-tenant
      deterministic jitter**: `cronOffsetMinutes = hashtext(tenant_id) mod 120`
      so a tenant lands on the same minute every night but the fleet spreads
      across a 2-hour window. Rolling-window scheduler is an acceptable
      alternative provided no two tenants in the same cluster start within the
      same 30-second slice. Why mandatory: a stock `0 3 * * *` cron fires every
      tenant's `DROP TABLE` simultaneously and thundering-herds Postgres WAL
      writers.
- [ ] Per tenant: scan `PlatformDbContext.TenantModules` where
      `IsDeleted = true AND (DeletedAt + retention_days) < now()`; retention
      resolved via `IConfigurationResolver.GetAsync<int>("modules.uninstall.retention_days")`
      (default 30, cap-bounded per ADR-0028).
- [ ] For each due row: iterate `DeletedTableNames`, issue
      `DROP TABLE IF EXISTS {schema}."{table}"` inside a per-table try/catch
      (one table failure MUST NOT block sibling drops), null the
      `DeletedTableNames` field, hard-delete the `TenantModule` row.
- [ ] Observability: counter `nexora_module_uninstall_purged_total{module}` +
      histogram `nexora_module_uninstall_purge_duration_seconds`. Per-tenant
      log line with tenant id + modules purged + rows dropped.
- [ ] Integration test (Testcontainers Postgres): seed `TenantModule` past
      retention, run job, assert tables dropped + row deleted; seed another
      within retention, assert untouched.
- [ ] Tests: unit (scheduler jitter math, retention predicate) + integration
      (end-to-end drop).
- [ ] Docs: `operations/migration-orchestration.md` gains a §"Uninstall purge"
      subsection describing the schedule + retention tuning.

## Technical notes

- Drop order within a tenant: `TenantModule.DeletedTableNames` is already in
  reverse-dependency order per the uninstall path; respect it so FK cascades
  land naturally.
- The job's own DbContext MUST use the platform schema (tenant-agnostic); the
  per-tenant drop fans out via an inner scope.
- `SetTenant(...)` called per inner iteration so structured logs carry the
  tenant id even though the job outer scope is platform-wide.
