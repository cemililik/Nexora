## Context

Phase 1.5.4 delivered the Portal Extension scaffolding (`PortalModuleManifest.slots`,
`<ModuleSlot>`, `<ModuleTabs>`, permission filtering, error-boundary isolation, and the
unit-tested cross-module contribution pattern in `src/Clients/nexora-portal/`) but
**no module currently contributes to a slot** — the `_registry.ts` module list is
still commented out pending the first real pilot. Per [ADR-0017](../../../decisions/0017-portal-extension-architecture.md)
"First pilot" section and the [`phase-2-enterprise.md`](../../../roadmap/phases/phase-2-enterprise.md)
Milestone A note (CRM chosen 2026-04-24 with rationale), CRM ships fully through
this mechanism — `module.manifest.yaml`, backend assembly endpoint, host-side
runtime registry, lazy chunk loading — and the lessons feed back into
[`docs/architecture/portal-extensions.md`](../../../architecture/portal-extensions.md).

This is the explicit Phase-1.5 → Phase-2 hand-off the bridge phase deferred:
"scaffold available, pilot deferred — by design, not by accident"
([phase-1.5-bridge.md §1.5.4](../../../roadmap/phases/phase-1.5-bridge.md)).

## Acceptance criteria

### Backend — manifest assembly endpoint
- [ ] `GET /api/v1/portal/manifests` shipped under the Portal Framework module.
      Returns `ApiEnvelope<AssembledManifestBundle>` (shape per
      [`portal-extensions.md` §3](../../../architecture/portal-extensions.md)).
- [ ] License gate filter applied — modules whose `license.requires` is not on the
      tenant's plan are dropped from the bundle (Phase 2 / dev: every Tier-2 module
      treated as `enterprise` and present; the `IEntitlementService` integration
      stays a Phase NMP follow-up).
- [ ] Permission filter applied per-route / per-menu-item / per-widget against the
      caller's permission set. Module is NOT dropped when the user lacks every
      permission — its i18n namespace may still be needed elsewhere.
- [ ] Cache: assembly result cached per `(tenantId, userId, licenseHash, moduleVersionHash)`
      in the L2 cache via `ICacheService` with TTL = shortest of contributing-module
      versions' TTLs. Invalidated on `tenant.entitlement.updated` and on tenant module
      install/uninstall events.
- [ ] Manifest schema validation on registration — invalid manifests are rejected with a
      structured error log; the offending module is excluded from the bundle but the
      bundle itself still ships (one bad module does not brick the host).

### Manifest schema artefact
- [ ] Single canonical schema file shipped at the path the runtime validator and the
      `validate-manifests` CI job both load from. Resolve the dual-path note in
      [`portal-extensions.md` §7](../../../architecture/portal-extensions.md) so the
      runtime path and the docs publish path are no longer ambiguous (one source of
      truth in `src/Nexora.Infrastructure/PortalExtensions/Schemas/`, with the docs
      directory either symlinked or generated from it at build time).
- [ ] CI job `validate-manifests` runs `ajv-cli` against every `module.manifest.yaml`
      in the repo; PR fails on schema violation.

### CRM frontend pilot
- [ ] `module.manifest.yaml` at the root of the CRM frontend package matching the v1
      schema. Carries `tier: 2`, `license.requires: enterprise`, exhaustive `permissions.declared[]`,
      `i18n.namespace: crm` with `[en, tr]` bundles.
- [ ] CRM contributes into **at least three host slot kinds** to exercise the manifest
      surface end-to-end:
  1. A new top-level navigation entry (`menu[]`) for `/crm/leads`.
  2. A tab into the existing Contacts 360° page (`widgets[]` keyed on
     `contacts.detail.tabs` slot) showing the contact's lead/activity history.
  3. A dashboard sidebar widget (`widgets[]` keyed on `dashboard.sidebar` slot)
     for "Recent leads".
- [ ] Lazy chunk loading verified — CRM JS is NOT in the host bundle when the tenant
      lacks the CRM module install or the `enterprise` license.
- [ ] Permission gate verified — a user without `crm.leads.read` sees the host's normal
      Contacts page with the lead-history tab absent (not an empty tab).

### Host loader — uncomment the registry
- [ ] `src/Clients/nexora-portal/.../_registry.ts` (currently commented out per
      `phase-1.5-bridge.md §1.5.4`) is uncommented and consumes the assembled bundle.
- [ ] `ModuleLoadErrorBoundary` smoke-tested: a deliberately-broken CRM chunk renders
      the boundary with retry; rest of the portal stays interactive.

### Tests
- [ ] Backend integration test: assemble a bundle for a tenant with CRM installed and
      a tenant without — assert per-route/widget/permission filtering and cache key
      correctness.
- [ ] Frontend round-trip: hydrate the registry from a fixture bundle, assert the
      navigation entry, contact-360° tab, and dashboard widget all render under the
      correct permissions.
- [ ] Architecture test: every Tier-2+ module in the repo MUST publish a
      `module.manifest.yaml`; a Tier-2 module without a manifest fails the build.
      Catches "we forgot to ship the manifest" drift as new Tier-2 modules land
      (Finance, Subscription, Projects).

### Locale
- [ ] `lockey_crm_module_name`, `lockey_crm_menu_*`, `lockey_crm_widget_*` keys in
      `en` + `tr` bundles. Module display name resolved from i18n, never a literal.

### Docs — pilot retrospective
- [ ] `docs/architecture/portal-extensions.md` gains a "Pilot retrospective" section
      capturing: (a) which manifest fields needed clarification mid-pilot;
      (b) any schema additions promoted into a v1 minor revision (additive only);
      (c) chunk-loading wall-clock measurements on a representative tenant; (d) one
      surprise per author (Backend + Frontend) so the next module author benefits.
- [ ] `phase-2-enterprise.md` Acceptance criterion *"Pilot retrospective merged into
      `architecture/portal-extensions.md`"* checked off when this lands.

## Technical notes

- The CRM module SPEC ([`../../../modules/tier-2-enterprise/crm/SPEC.md`](../../../modules/tier-2-enterprise/crm/SPEC.md))
  already declares a 360° contribution back to Contacts via an event-driven cache —
  the manifest tab is the UI surface of that contract, not a new design.
- The widget slot IDs (`contacts.detail.tabs`, `dashboard.sidebar`) MUST be exposed
  by the host shells before this task starts; if they are not yet declared, file a
  precursor task on the Portal Framework module rather than ad-hoc-introducing them
  in this PR.
- Manifest cache key `moduleVersionHash` is the SHA-256 of the concatenated `id@version`
  strings of all installed modules sorted by id — stable across processes and
  cluster nodes.
