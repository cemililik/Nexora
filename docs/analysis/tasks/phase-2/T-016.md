## Context

Multi-cluster rollouts use Flux/ArgoCD progressive delivery; platform itself should
integrate a feature-flag service (LaunchDarkly evaluation or native
`ITenantConfiguration` as feature-flag store) so specific features can be rolled
out per tenant cohort instead of per platform version.

See `docs/operations/license-and-helm-upgrade.md` §6.4.

## Acceptance criteria

- [x] `IFeatureFlagService` abstraction with `IsEnabledAsync(flagKey, userId?, ct)` + `SetAsync` + `GetAllAsync`. The optional `userId` parameter is the dimension future percentage-rollout backends can hash on; default backend ignores it.
- [x] Default implementation: `TenantConfigFeatureFlagService` reads/writes through `ITenantConfiguration` under the `feature_flags.{key}` namespace.
- [x] DI is set up so a future `LaunchDarkly` backend swaps the registration without touching call sites — the `IFeatureFlagService` registration in `IdentityModule.ConfigureServices` is the single replacement point.
- [x] Admin endpoints under `/api/v1/identity/feature-flags`: GET list, GET single, PUT toggle. Permission `identity.feature_flags.manage` (Platform-scope).
- [x] 7 unit tests cover absent-flag default-off, set→read round-trip, true→false flip, list returns only flag-prefixed keys, prefix isolation, userId pass-through (current backend ignores it), empty-key argument validation.
- [x] Lockeys for the new permission added in `identity.json` (en + tr).

**Deferred (UI-side):**

- [ ] Admin dashboard React page to render the listing + toggle UI. The backend surface this PR ships is the contract; the UI work is straightforward against the documented endpoints and is filed as a Milestone C UI follow-up so this PR's review can stay backend-focused.
