# T-027: GDPR erasure escape hatch for renamed uninstall tables

- **ID:** T-027
- **Status:** Done
- **Owner:** maintainer (autonomous agent)
- **Phase:** phase-2
- **Milestone:** A
- **Created:** 2026-04-24
- **Last updated:** 2026-04-25

## Context

GDPR Article 17 erasure (T-004) redacts a contact's rows from every module's
canonical tables. Under the [ADR-0028](../../../decisions/0028-module-uninstall-data-retention-contract.md)
uninstall contract, tables rename to `{module}_{table}_del_{timestamp}` and
remain for a retention window. Without an escape hatch, an erasure request
that lands during the retention window silently leaves the renamed tables
untouched — a compliance leak: the tenant asked for Article 17 erasure and
the canonical row was cleared, but the renamed `_del_` copy still carries
the data.

The escape hatch is deliberately **module-local** — each module's
`ContactGdprDeletedIntegrationEventHandler` scans only its *own* renamed
tables. Cross-module reach is not this task's concern; that is owned by
[ADR-0026](../../../decisions/0026-cross-module-pii-payload-scan-for-gdpr-erasure.md) / T-010.

## Acceptance criteria

- [ ] `ContactGdprDeletedIntegrationEventHandler` in every module that handles
      the event (Contacts, Documents, Notifications, Audit today; CRM /
      Subscription / Finance when they land) gains a **second-pass scan**
      after the canonical-table redaction:
  1. Query `information_schema.tables` for tables whose name matches
     the canonical uninstall-rename shape (`{module}_{entity}_del_{timestamp}`
     per ADR-0028 / T-025). The naïve form
     `table_name LIKE '{module}_%_del_%'` is **unsafe** — SQL `LIKE`
     treats `_` as a single-character wildcard, so `contacts_` would
     match `contactz` and a future module whose name is a prefix of
     another (`notifs` vs. `notifs_ext`) would cross-bleed. Use ONE of:
     - **Escaped `LIKE`**: literal underscores escaped via an explicit
       escape character, e.g. `LIKE '{module}\_%\_del\_%' ESCAPE '\\'`
       (with `{module}` itself passed as a parameter whose value is
       pre-escaped for `_` and `%`), OR
     - **Regex match** (preferred, more explicit): `table_name ~ '^{module}_[a-z0-9_]+_del_([0-9]{14}|[0-9]{8}_[0-9]{6})$'`
       — anchored at both ends, requires the `_del_` marker as literal
       text (not wildcard), and accepts either timestamp form (14-digit
       contiguous OR `yyyyMMdd_HHmmss`) — matches T-025's canonical
       whitelist regex which accepts both producer formats from T-026.
       The `{module}` placeholder MUST still be escaped for regex
       metacharacters before interpolation; in practice module names
       are snake_case ASCII (validated at module-registration time),
       so the escape is a defence-in-depth measure.
     Note: **module-prefixed only** — Contacts must NOT scan Finance's
     renamed tables.
  2. For each renamed table, run the same redaction SQL that was applied to
     the canonical table, matched on `ContactId` + `TenantId`.
- [ ] The scan is idempotent: if a renamed table's matching rows are already
      redacted (the canonical handler ran before), the SQL UPDATE affects 0
      rows and the pass is a no-op.
- [ ] Observability: per-module log line
      `"GDPR erasure: redacted {RowCount} rows across {RenamedTableCount} renamed tables for contact {ContactId}"`.
      Counter `nexora_gdpr_erasure_renamed_table_scans_total{module}`.
- [ ] **Architecture test**: a new `GdprEscapeHatchBoundaryTest` in
      `Nexora.Architecture.Tests` fails CI when a module handles
      `ContactGdprDeletedIntegrationEvent` but its handler source does not
      call the shared `ScanRenamedTablesAsync(...)` helper. Keeps future
      modules honest.
- [ ] Shared helper `GdprRenamedTableScanner` in
      `Nexora.SharedKernel.Abstractions.Gdpr` (or Infrastructure — pick based
      on whether it needs EF Core) exposes the table-discovery + redaction
      loop so each module handler calls one method.
- [ ] Integration test (Testcontainers Postgres): uninstall a module's
      entity, trigger erasure event, assert renamed-table row is redacted.
- [ ] Docs: `docs/modules/tier-1-core/contacts/SPEC.md` §GDPR extends the
      erasure flow diagram to show the renamed-table scan step.

## Technical notes

- Table-discovery query runs inside the tenant's search_path, so no explicit
  schema prefix needed.
- SQL injection safety: `module` and `table_name` are module-declared
  constants (not user input), but the helper still uses Npgsql quoted
  identifiers for defence in depth.
- The escape hatch is **not** responsible for redacting audit-trail rows
  (those live in Audit module's retention window and are handled by ADR-0008
  rules — not ADR-0028).
