## Context

`/health/ready` currently registers a single health check
(`OutboxHealthCheck`). Postgres, the Dapr sidecar, and every other
runtime dependency are invisible to the readiness probe — if Postgres
is unreachable but the outbox query happens to pass (or the outbox
table was populated earlier), the endpoint returns 200 and Kubernetes
keeps the pod in the load-balancer pool. The outage becomes "500s on
the first real request" instead of "readiness gate fails, pod stays
out of rotation".

T-023 adds first-class health checks for the two critical
infrastructure dependencies the API cannot run without:

- **Postgres** (every module's DbContext).
- **Dapr sidecar** (state store, pub/sub, secrets — everything routes
  through it).

Keycloak and MinIO are reachable via Dapr in production, so the
sidecar check covers them transitively. A first-class Keycloak check
adds a network hop to every readiness poll (Kubernetes polls it every
10s by default) and risks flapping under Keycloak maintenance windows;
rejected in favour of "fail on first auth attempt" surfacing that
downstream outage.

## Technical notes

- Postgres check uses `NpgsqlConnection` directly (not EF) so a
  DbContext misconfiguration does not mask a connectivity issue.
- Dapr check uses `IHttpClientFactory` with a named
  `"dapr-healthz"` client; timeouts on the factory, not
  `CancellationTokenSource`, so we don't leak task objects on hot
  paths.
- Both checks return `HealthCheckResult.Unhealthy` with the caught
  exception message — never silently degraded. Kubernetes treats
  Degraded as Ready; if the dep is actually down, Unhealthy is the
  right signal.
- `data` dict contains `latency_ms` so Grafana dashboards can chart
  readiness latency without adding a separate metric.
