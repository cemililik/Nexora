## Context

`ContactExportJob.ExecuteAsync` currently emits the completion notification
(`SendNotificationRequest` with `lockey_contacts_notification_export_ready`)
inline at the end of the job. It is guarded by `startedFromQueued` so a
resume / retry of the same Hangfire job does NOT re-send — the trade-off
is that a crash between `MarkProcessing` and `SendAsync` results in
**missed** notification rather than duplicated.

The current source carries an extensive comment explaining the design and
naming the planned end-state (consume
`ContactExportCompletedIntegrationEvent` in a separate inbox-guarded
handler with a stable dedupe key `contacts:export-ready:{jobId}`). The
two earlier maintainer reviews (commits `576ff65` and `0ad2baa`)
explicitly accepted the trade-off pending this follow-up task. T-028
is the follow-up — it ships the inbox-guarded consumer so the job
becomes:

- **Outbox-only on job side**: `ContactExportCompletedIntegrationEvent`
  is the single source of truth.
- **Inbox-guarded consumer**: `ContactExportCompletedNotificationHandler`
  in the Notifications module receives the event, dedupes via
  `contacts:export-ready:{jobId}`, sends the notification.
- **Removes `startedFromQueued` gate** in `ContactExportJob.ExecuteAsync`.

The result: notification becomes idempotent end-to-end (guaranteed
delivery on success, never a duplicate on resume).

## Acceptance criteria

- [ ] New
      `Nexora.Modules.Notifications.Infrastructure.IntegrationEvents.ContactExportCompletedNotificationHandler`
      consumes `ContactExportCompletedIntegrationEvent`.
- [ ] Inbox guard uses dedupe key `contacts:export-ready:{jobId}` —
      assigned at queue time, stable across retries, unique per export.
- [ ] `ContactExportJob.ExecuteAsync` no longer calls
      `notificationService.SendAsync(...)` directly. The
      `startedFromQueued` gate around the notification block is
      removed; the outbox event is always emitted.
- [ ] Integration test: queue an export, complete it, observe a single
      notification. Re-emit the same event id; observe the inbox guard
      short-circuits (no second notification).
- [ ] The existing comment block in `ContactExportJob.ExecuteAsync`
      (referencing T-010 / T-017) is removed since the planned end-state
      lands in this task. Replace with a one-line note pointing at the
      new handler.

## Technical notes

- The dedupe key is constructed from the export's `JobId` (Guid) so the
  same key is produced regardless of how many times the message is
  redelivered.
- Notifications module already implements the inbox pattern for
  `ContactGdprDeletedIntegrationEvent` (see T-004 WP3). T-028 follows
  the same shape — `IInboxGuard` + `IsAlreadyProcessedAsync` +
  `MarkAsProcessed`.
- No schema change required; the Notifications inbox table already
  exists.
