## Context

`permissions.md` §3 and ADR-004 (Accepted) both mandate that **each module declares its
own permissions in `IModule.OnStartupAsync` via `IPermissionRegistry`**. The code has
drifted from this contract:

- `IPermissionRegistry` does not exist in SharedKernel.
- Every module's `OnStartupAsync` is an empty hook with a comment saying "permissions are
  seeded centrally in `IdentityModuleMigration.SeedAsync`".
- `IdentityModuleMigration.SeedAsync` carries one flat list for **all** modules (Identity
  knows about Contacts, Documents, etc. — a module-boundary violation).
- `DevelopmentSeed.CreateDefaultPermissions()` is a **second, parallel** list used only in
  dev startup. The two lists have already diverged (e.g. `audit.logs.export` vs
  `audit.logs.write`, `identity.tenants.create/update/delete` missing from one side).
- Tenant-admin role "Platform Admin" is assigned **Platform-scope permissions** at seed
  time (`identity.tenants.*`), contradicting `permissions.md` §2: *"Platform permissions
  are never assignable to a tenant-scope role; tenant permissions are never granted to
  platform-scope roles. Enforced by the permission registry at seed time."*

None of this requires a new ADR — we are aligning code with an already-Accepted standard
and ADR. This task pays that tech debt off.

- Phase file: `../../roadmap/phases/phase-1.5-bridge.md` §1.5.6
- Related standards: `docs/standards/permissions.md` §2, §3
- Related ADRs: ADR-004 (centralized permission seeding — Accepted), ADR-0016 (scope model),
  ADR-0025 (org-scoped compliance — added `contacts.gdpr.settings_manage`).
- Related tasks: T-019 (just shipped; introduced `contacts.gdpr.settings_manage` and
  `platform.compliance.policy_manage`). The audit-perms + `contacts.contacts.*` endpoint
  fixes landed as a hotfix alongside T-019 review; this task removes the class of bug that
  allowed them to happen.

## Acceptance criteria

- [ ] `IPermissionRegistry` interface in `Nexora.SharedKernel.Abstractions.Authorization`
      (or equivalent existing namespace). Supports `Register`, `IsRegistered`, `GetAll`,
      `GetByModule`. Registers throw on duplicate keys.
- [ ] `PermissionDefinition(string Module, string Resource, string Action, string DescriptionKey, PermissionScope Scope)`
      record in SharedKernel, produced by `Register(...)`.
- [ ] `InMemoryPermissionRegistry` singleton in `Nexora.Infrastructure` + DI registration.
- [ ] `IModule.OnStartupAsync` signature updated to accept `IPermissionRegistry` (breaking
      change internal to the project; all 6 modules updated).
- [ ] Each of the 6 modules registers its own permissions in `OnStartupAsync`:
      Identity, Contacts, Documents, Notifications, Reporting, Audit. No cross-module
      registrations.
- [ ] `IdentityModuleMigration.SeedAsync` reads the full permission set from the registry
      (not a hardcoded list). Hardcoded `Permission.Create(...)` array removed.
- [ ] `IdentityModuleMigration` top-up path reads the registry and inserts any missing
      permissions — no separate `newPermissionsToEnsure` hardcoded list.
- [ ] `DevelopmentSeed.CreateDefaultPermissions()` deleted. Dev-tenant seed reuses the
      module-migration path (either by running it directly or by pointing the dev tenant
      through `TenantSchemaManager.MigrateAllModulesAsync`).
- [ ] Role seed enforces scope rule: the tenant-side "Platform Admin" role receives
      **only `PermissionScope.Tenant`** permissions. A maintenance step in the same
      seed **removes** any existing Platform-scope assignments from tenant roles (idempotent).
- [ ] New permissions added by a module automatically flow into existing Platform Admin
      role via the generic top-up (no separate list to update).
- [ ] Tests — unit:
  - Registry: register + duplicate detection + scope filtering + IsRegistered.
  - IdentityModuleMigration: seeds from registry, inserts missing, skips duplicates,
    Platform Admin role gets only Tenant-scope perms.
- [ ] Tests — architecture:
  - `IdentityModuleMigration` must NOT contain hardcoded cross-module permission strings
    (NetArchTest or regex-based file scan).
  - `DevelopmentSeed` must NOT contain hardcoded `Permission.Create(...)` calls.
  - Every module class referenced in `NexoraModuleRegistration` must call
    `registry.Register(...)` at least once (verified reflectively).
- [ ] Tests — integration (one new):
  - Fresh tenant schema + module registration → all modules' permissions present +
    Platform Admin role has every Tenant-scope perm and zero Platform-scope perm.
- [ ] Locale: no new user-facing strings — all `lockey_` keys for permissions already exist.
- [ ] Runtime smoke: `docker compose up`, `/health` ok, `/api/v1/identity/permissions?scope=Tenant`
      returns the full set (same count as before ± delta for any genuinely-new perms).
- [ ] Docs:
  - `permissions.md` §3 example code updated if the final `OnStartupAsync` signature
    differs from the standard's example.
  - CHANGELOG entry.
  - T-019 final review comment referencing T-020 closure of the "double seed source"
    observation.

## Technical notes

- **Migration compatibility:** `platform.compliance.policy_manage` must continue to exist
  as a Platform-scope permission (from T-019). It stays in the Identity module's registration.
- **Leftover Platform-scope assignments:** existing dev tenant currently has
  `identity.tenants.create/update/delete` assigned to Platform Admin (pre-existing bug).
  The seed's idempotent "strip-Platform-scope-from-tenant-roles" step cleans them up on
  next startup. No manual DB intervention needed.
- **`identity.tenants.*` endpoints:** `TenantEndpoints.cs` uses `identity.tenants.manage`
  on `PUT /{id}/settings`. Other tenant-mutation endpoints (`POST /`, `PUT /{id}/status`)
  have only base `RequireAuthorization()` — pre-existing gap, slated for NMP.3 migration.
  Not widened by this task.
- **Breaking change scope:** `IModule.OnStartupAsync(CancellationToken)` →
  `IModule.OnStartupAsync(IPermissionRegistry, CancellationToken)`. Only 6 internal
  implementations; no public API surface affected.
- **Registry lifetime:** singleton. Populated once at host startup; read once at tenant
  seed time. No per-request mutation.
