# T-005: `SeedDemoData()` method on `IModule`

## Context

Phase 2 modules need a consistent way to declare demo data. Extend the `IModule` contract
with an optional `SeedDemoData(ITenantContext, CancellationToken)` method so each module
owns its demo content and avoids a central seeding god-object.

- Phase file: `../../roadmap/phases/phase-1.5-bridge.md` §1.5.7
- Legacy reference: `docs/roadmap/ROADMAP.md` §1.5.7 item 1
- Related ADRs: ADR-001 (modular monolith), module system contract in
  `docs/architecture/MODULE_SYSTEM.md`

## Acceptance criteria

- [x] `IModule.SeedDemoDataAsync(TenantDemoSeedContext, CancellationToken)` method
      added with a default no-op implementation (C# default interface method — no
      existing module had to change).
- [x] `DemoDataSeeder` orchestrator (`Nexora.Infrastructure.Modules.DemoDataSeeder`)
      resolves installed modules, topologically sorts by `IModule.Dependencies`,
      and invokes each in one DI scope per module.
- [x] Idempotent: re-running against an already-seeded `(tenant, module, scenario)`
      tuple short-circuits based on the `platform_demo_seed_markers` tenant-schema
      table. A different scenario re-runs the same module (tested).
- [x] Unit tests in `DemoDataSeederTests`: ordering (wrong-order input reordered
      correctly), idempotency (second run = AlreadySeeded), scenario separation,
      broken-sibling isolation (one failing module does not block others), cycle
      detection, missing-dependency detection, tenant-id validation.
- [x] Architecture test in `DemoDataSeedingBoundaryTests`: module assemblies
      cannot depend on each other's `Infrastructure` namespace (catches a future
      module that tries to seed another module's data directly). Plus a contract
      lock that pins the `SeedDemoDataAsync` signature.
