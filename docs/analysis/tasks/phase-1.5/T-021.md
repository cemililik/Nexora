## Context

T-018's Testcontainers integration test for `GdprHardDeleteJob` surfaced a
pre-existing drift in the Contacts module's EF configurations:
`ContactTagConfiguration` and `ContactCustomFieldConfiguration` both declare

```csharp
builder.HasIndex(...).IsUnique().HasFilter("\"IsDeleted\" = false");
```

on entities that extend `Entity<TId>`, **not** `AuditableEntity<TId>`. The
`IsDeleted` column therefore does not exist on those tables, so the filter
predicate references a non-existent column.

Dev works only because the live schema pre-dates the filter — `contacts_contact_tags`
and `contacts_custom_field_values` were created before the filter clause was
added, and the dev DB has been patched by hand since. A fresh
`GenerateCreateScript()` against a clean Postgres fails with

```text
42703: column "IsDeleted" does not exist
```

at the CREATE INDEX step. T-018 worked around it with a targeted skip in the
integration test's DDL loop and logged a follow-up — this is that follow-up.

## Acceptance criteria

- [x] Remove `.HasFilter(...)` from `ContactTagConfiguration`; comment records
      the rationale so a future reader doesn't re-add it.
- [x] Remove `.HasFilter(...)` from `ContactCustomFieldConfiguration`; same
      rationale comment.
- [x] Unique semantic unchanged: `ContactTag` / `ContactCustomField` are
      hard-deleted on removal, never soft-deleted. The filter was dead code.
- [x] `GdprHardDeleteJobTenantRoutingTests` now uses plain
      `IRelationalDatabaseCreator.CreateTablesAsync()` (one transaction, no
      statement-by-statement loop, no 42703 skip). Dropped the ~60-line
      `SplitDdlStatements` / `IsValidDollarTag` helpers that existed only to
      work around the drift.
- [x] Full suite green (~1961 backend tests including the 2 T-018 integration
      tests that exercise the clean CREATE path).

## Technical notes

- The dev DB currently shows the index without the filter
  (`IX_contacts_contact_tags_...` is a plain unique btree); removing
  `.HasFilter()` from code aligns EF's view of the model with the actual DB
  state, so there is no runtime schema change.
- The index was never logically "partial" — the filter was dead code.
- T-022 (next in the batch) adds an architecture test that prevents this
  drift re-entering the codebase.
