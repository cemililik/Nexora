## Context

Replaces the "T-007a" partition of the now-superseded [T-007](T-007.md). T-007's
acceptance criteria assumed CRM, Finance, Projects (Phase 2) and Fundraising,
Sponsorship, Events (Phase 3a) modules existed; they do not. The carry-over
sweep on 2026-04-24 split T-007 into three tracks (see T-007 status log):

- **T-029 (this task)** — registry plumbing + the Contacts-only seed slice that
  is implementable today against the modules that already ship.
- **Per-Phase-2-module seed tasks** — filed at each module's kickoff inside
  Phase 2 (CRM, Finance, Subscription, Projects). Tracked in the Phase 2 task
  set as those modules begin work; not pre-allocated to avoid stub bloat.
- **Per-Phase-3a-module seed tasks** — same pattern, filed at each Phase 3a
  module's kickoff (Fundraising, Sponsorship, Events).

The registry that lands here is the contract those later tasks fill in: each
new module that ships demo content registers its scenario contributions
through `IDemoScenarioRegistry`, and the admin dialog (T-008) reads from the
same registry instead of the current hardcoded `general` / `ngo` dropdown.

## Acceptance criteria

- [ ] `DemoScenario` record in `Nexora.SharedKernel.Abstractions.Modules`:
      `Name` (string, kebab-case), `DescriptionLockey` (string), `RequiredModules`
      (`IReadOnlyList<string>`), `OptionalModules` (`IReadOnlyList<string>`).
- [ ] `IDemoScenarioRegistry` interface + `InMemoryDemoScenarioRegistry` default
      implementation, both in `Nexora.SharedKernel.Abstractions.Modules`. Registry
      pre-populates `general` and `ngo` scenarios; modules registered through DI
      append their own scenarios via `IDemoScenarioContribution` collected from
      the service container at composition time.
- [ ] `GET /identity/demo/scenarios` endpoint — platform-scope, gated on the
      existing `platform.tenants.create_demo` permission (added in T-008). Returns
      `ApiEnvelope<List<DemoScenarioDto>>` with the scenarios whose
      `RequiredModules` are all installed for the current tenant; the others are
      filtered out. Empty list is a legitimate response (no modules support a
      scenario yet — caller renders an empty state).
- [ ] Contacts module `SeedDemoDataAsync` implements **both** scenarios:
  - `general`: ~20 business contacts (mix of `Individual` + `Company` types,
    staff and clients spread across at least 3 region/locale shapes,
    realistic-but-locale-neutral names, `example.com` emails).
  - `ngo`: ~30 donor contacts with diverse donation-history shapes (one-time,
    recurring monthly, lapsed, major donor), `example.org` emails. Pure
    contacts only — no donation rows; that is owned by the Phase 3a Fundraising
    seed task.
  - Both seeds idempotent on natural keys (email lowercased) so a re-run
    against an existing seed produces zero new rows.
- [ ] Architecture test in `tests/Nexora.Architecture.Tests/`: every module
      declared in any registered scenario's `RequiredModules` MUST implement
      `IModule.SeedDemoDataAsync` with non-default content (i.e.
      `DemoDataSeeder.IsDefaultNoOp` returns `false` for that scenario). Catches
      "registered but inert" drift where a future module landed in
      `RequiredModules` without anyone wiring its seed.
- [ ] Admin dialog (T-008) refactor: `CreateDemoEnvironmentDialog` swaps its
      hardcoded dropdown for `useDemoScenarios()` (TanStack Query) calling the
      new endpoint. Empty list path renders the existing `EmptyState`
      component with a translated message. Shipped in the same PR as the
      backend work to keep the dialog honest.
- [ ] Locale: `lockey_demo_scenario_general_name`,
      `lockey_demo_scenario_general_description`, `lockey_demo_scenario_ngo_name`,
      `lockey_demo_scenario_ngo_description` in `en` + `tr` bundles. No raw
      English strings in the registry seed.
- [ ] Tests: unit (`InMemoryDemoScenarioRegistryTests` for filtering by
      installed-module set, idempotent registration; `ContactsDemoSeedTests`
      for both scenarios — count + idempotency). Architecture test for the
      drift guard above.
- [ ] Docs: `docs/analysis/tasks/phase-1.5/T-008.md` Status log updated to
      record the dialog refactor; `docs/standards/audit-coverage.md` unchanged
      (demo seeding remains MAY AUDIT — the seed itself is a development action,
      not a compliance event).

## Technical notes

- Domain-expert review of the seed content shape (donor cohort distributions,
  recurring-vs-one-time ratios, name diversity) is part of the implementation
  budget — flag this in the PR for at least one product-side reviewer. The
  3-5-day estimate in T-007's status log includes this review loop.
- **Out of this task's scope on purpose**:
  - CRM pipeline content for `general` scenario → ships with CRM module
    (Phase 2 task to be filed when CRM kickoff happens).
  - Finance entries, Project tasks → same pattern, with their respective
    Phase 2 modules.
  - Donation rows, sponsorship pairings → ship with Phase 3a Fundraising /
    Sponsorship modules.
- Registry filtering MUST consult `IModuleAvailability` (added in T-005) when
  registered. Falls back to "every DI-registered module is available" when
  `IModuleAvailability` is not registered, matching the orchestrator's current
  Phase 1.5 behaviour.
- The `lockey_demo_scenario_*` keys join the existing `lockey_demo_*` namespace
  the T-008 dialog already uses; no new namespace.
