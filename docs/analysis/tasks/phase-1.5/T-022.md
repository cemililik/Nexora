# T-022: Architecture guard — `HasFilter("\"IsDeleted\"...")` must target `ISoftDeletable` only

- **ID:** T-022
- **Status:** Done
- **Owner:** cemililik
- **Phase:** phase-1.5
- **Milestone:** C (preventive follow-up to T-018 / T-021)
- **Created:** 2026-04-23
- **Last updated:** 2026-04-24

## Context

T-018's Testcontainers integration test exposed that
`ContactTagConfiguration` and `ContactCustomFieldConfiguration` declared
`HasFilter("\"IsDeleted\" = false")` on indexes whose target entities did
NOT implement `ISoftDeletable` — a silent drift that only manifests
against a fresh Postgres, and that T-021 just cleaned up.

Without a preventive test, the same drift can re-enter the codebase as
soon as a future module copy-pastes a configuration snippet. T-022 adds
an architecture test that walks every EF `IEntityTypeConfiguration<T>` in
every module assembly and asserts: a configuration that calls
`HasFilter(...)` referencing the `IsDeleted` column only applies to
entity types that implement `ISoftDeletable`.

## Technical notes

- EF's `IMutableIndex.Filter` is a `string?`; the test can match on
  any occurrence of `"IsDeleted"` (substring) rather than requiring a
  specific form — catches `"IsDeleted" = false`, `NOT "IsDeleted"`,
  `"IsDeleted" IS FALSE`, etc.
- Building a `ModelBuilder` requires only a `ConventionSet`; we use
  `NpgsqlConventionSetBuilder.Build()` from
  `Npgsql.EntityFrameworkCore.PostgreSQL` (already transitively
  referenced by module assemblies).
- Scanning is module-local; the test iterates
  `ModuleAssemblies()` (same helper used by
  `DemoDataSeedingBoundaryTests`) so no module is missed and adding
  a new module does not require touching this test.
- Alternative considered: a static analyzer (Roslyn) that inspects
  the source file text for the pattern. Rejected — less precise
  (misses `HasFilter("IsDeleted IS FALSE")` etc.), and we already
  have the EF model in hand so runtime inspection is strictly
  better.
