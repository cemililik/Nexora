## Context

The current GDPR deletion flow only anonymizes PII and soft-deletes the contact. GDPR
Article 17 requires **physical removal**. This task adds a true hard-delete path with
cross-module cleanup, while preserving consent records as legal evidence (Article
17(3)(e)).

- Phase file: `../../roadmap/phases/phase-1.5-bridge.md` §1.5.6
- Legacy reference: `docs/roadmap/ROADMAP.md` §1.5.6 item 4
- Plan doc: `.claude/plans/gdpr-hard-delete.md` (legacy location; migrate if still present)
- Related ADRs: ADR-008 (GDPR deletion strategy), ADR-014 (distributed consistency)

- [x] Locale: `lockey_contacts_gdpr_erasure_{enqueued,completed,failed}` keys in en + tr.

## Technical notes

- Hard delete is one of the three sanctioned hard-delete paths in CLAUDE.md (alongside
  join-table reconciliation and module uninstall).
- Cross-module consumers must use the inbox pattern (ADR-014) for idempotency.
- Coordinate un-linking with T-001 (`User.ContactId` must become null).

### Known deviations / follow-ups (for maintainer review)

1. **`BaseDbContext.IsHardDeleteModeEnabled` flag** — introduced in WP1 to scope the
   `ExecuteDeleteAsync` soft-delete bypass explicitly to this compliance path. Shared
   infrastructure change; intentional.
2. **Notifications `BodyRendered` scrubbed to `[REDACTED]`, not `null`** (WP3). Column is
   currently non-nullable. Future schema migration can relax if strict null is required.
3. **Admin UI locale keys are unprefixed** (`gdpr_erasure_button` etc., not
   `lockey_contacts_gdpr_erasure_button`). Diverges from existing `lockey_*` convention
   in `contacts.json`. Maintainer may wish to rename for consistency.
4. **Audit payload JSON scan not implemented (WP4)** — handler only targets
   `EntityType=Contact AND EntityId=<contactId>`. Payload-containment scan across other
   audit entries mentioning the contact is deferred (unindexed, high false-positive risk).
5. **`User.ContactId` unlink handler** — not present; Identity will add it in T-001.
